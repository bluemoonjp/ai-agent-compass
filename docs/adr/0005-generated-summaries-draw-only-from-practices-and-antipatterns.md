# ADR-0005: Generated summaries draw only from practices/ and antipatterns/

Status: accepted

Issue: #25
Date: 2026-09-18

## Context

An agent scanning this repository for guidance needs a cheap way to see what exists — which practice ids, rules, topics, and tools apply — without opening every file under `practices/`. A hand-maintained summary of that same information, kept beside the source files it summarizes, is the same failure mode `docs/maintain/authoring.md`'s check table already generates by `pnpm gen` from `checks.json` to avoid (see `generated-fresh`): two representations of one fact, one of which a human has to remember to update by hand every time the other changes.

`practices/` and `antipatterns/` already carry the only fields (`id`, `rule`, `topic`, `applies_to`, `sources[].verified_on`) an index or a plugin reference needs. Deriving a summary from them at `pnpm gen` time, instead of writing it a second time, extends the check table's existing generation mechanism to further generated surfaces.

## Decision

`practices/` and `antipatterns/` are the only canonical source a generated summary may draw from. `practices/index.md`, the README's practice-count block, and (from #26 on) a plugin skill's `references/` files are all generated by `pnpm gen` from `practices/`, `antipatterns/`, and `checks.json`, never hand-edited, and checked for staleness by `generated-fresh` the same way the check table already is. This decision does not claim every other file in the repository is generated — `templates/`, `adapters/`, and a plugin's `SKILL.md` body remain hand-authored canonical content in their own right (ADR-0001's layer A); it only scopes what a *generated summary* is allowed to summarize.

Three alternatives were considered and rejected:

- **Make the plugin's copy canonical instead.** Installing a plugin only copies `plugins/<name>/`; `templates/`, `adapters/`, and the rest of layer A (ADR-0001) live outside that directory and would have no canonical home under this option. It would not centralize canon, only relocate part of it to a narrower directory that cannot hold the whole deliverable.
- **Keep hand-maintaining a duplicate.** `docs/maintain/authoring.md`'s check table is already generated by `pnpm gen` from `checks.json` specifically because a hand-maintained copy of another file's fields silently drifts the moment either side changes without the other being updated; `generated-fresh` exists to catch exactly that shape of drift. Writing a practice index by hand would reintroduce the same failure mode the check table's own generation already exists to prevent, with nothing left to catch it this time.
- **Link only, without generating an index.** A bare link to `practices/` gives a reader no way to compare `id`, `rule`, `topic`, `applies_to`, and `verified_on` across files without opening each one. It satisfies "point at the canon" but not the reason an index is wanted in the first place: cheap, at-a-glance scanning by an agent that has not yet decided which practice file is relevant.

Retiring a practice follows the deletion-plus-obsolete-antipattern procedure `docs/maintain/authoring.md` already states; this ADR does not restate it.

## Consequences

A practice's `id`, `rule`, `topic`, `applies_to`, and oldest `sources[].verified_on` now appear in exactly one place a human edits (the practice file itself); `practices/index.md` and the README's generated block are regenerated by `pnpm gen` and rejected as stale by `generated-fresh` if they are not. Adding a practice, editing its `rule`, or changing its `status` and forgetting to run `pnpm gen` now fails `pnpm check` with a message naming the command to run, instead of silently leaving the index wrong.

`antipattern.schema.json`'s `relates_to` field is `minItems: 1` and, per `frontmatter-schema`'s `unresolved-relates-to` check, every id in it must resolve to a practice file that still exists. `docs/maintain/authoring.md`'s retirement instructions already account for both constraints; this ADR does not restate them.
