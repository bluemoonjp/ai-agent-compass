# ADR-0009: A fork or Dependabot PR's private-pattern paste check runs for real in a second `workflow_run` workflow, instead of relaying a notification the first job cannot send

Status: accepted

Issue: #109
Date: 2026-09-19

## Context

`public-surface.yml`'s `check-paste` job declares `permissions: issues: write, pull-requests: write`, and its "Flag needs-redaction"/"Flag needs-owner-recheck" steps use that to label and comment on the issue or PR it scanned. For a `pull_request` run whose head is a fork, GitHub Actions overrides that declaration: `GITHUB_TOKEN` is forced read-only, and no repository secret is passed, regardless of what the workflow file requests. The same restriction applies to a `pull_request` run opened by Dependabot, even though Dependabot's branch lives inside this repository rather than an actual fork — GitHub treats it identically for token and secret purposes. Every such run's `gh api` calls to add a label or post a comment therefore return 403, and `COMPASS_PRIVATE_PATTERNS` is unset in that run regardless of whether it is actually configured for this repository.

A second, related gap sat in the same step: `check-paste`'s exit code did not distinguish "the private-pattern check itself could not run" (`COMPASS_PRIVATE_PATTERNS` unset) from "a generic pattern actually matched the text" (an email address, a Windows path — these run unconditionally). A fork or Dependabot PR whose body genuinely contained a private-information-shaped string got the "could not check" message instead of the "a match was found" one, and never received the `needs-redaction` label.

`pull_request_target` would hand this job an unrestricted token and real secrets, but ADR-0008 already rules it out repository-wide, for the reason stated there: it runs in the base repository's privileged context while typically evaluating the fork's own commit. This decision does not reopen that question — and the design below turned out to need that same caution applied one level further than an earlier draft of it assumed, and to revisit an assumption of its own once that draft was corrected.

An earlier version of this decision had `check-paste`'s job write its own verdict (a PR number and an exit code) to an artifact, and a second, `workflow_run`-triggered workflow read that artifact and post from it. That design has a real flaw: GitHub runs a `pull_request` (not `pull_request_target`) job using the workflow *file* as it exists on the pull request's own branch, not a copy pinned to the base branch. A fork PR author can therefore rewrite `check-paste`'s own steps — including the one that writes the artifact — in their own PR branch, and have it upload an arbitrary PR number alongside `exit_code: 1`. Artifact upload does not need the restricted `GITHUB_TOKEN`, so this works even under the fork/Dependabot token restriction. The second workflow's privileged, unrestricted token would then post the fixed-wording `needs-redaction` label and comment onto whatever issue or PR number the artifact named — a label/comment-injection primitive against arbitrary issues or PRs, introduced by the fix itself. Pinning `check-paste`'s `actions/checkout` step to the base commit (still done, see below) protects only the *checked-out code* `check-paste.mjs` reads; it does nothing for the surrounding job's own step definitions, which remain attacker-editable for exactly the same reason `pull_request_target` exists as a distinct trigger.

Closing that gap — by having the second workflow re-derive the PR and its body from GitHub's API instead of trusting an artifact — surfaced a second, independent correction: `workflow_run` gives its job a normal `GITHUB_TOKEN` *and* normal secret access, unlike the `pull_request` job it follows. That means the second workflow does not need to relay "the check could not run, an owner should recheck manually" at all — it can simply run the check itself, with the real secret, and report only what that run actually finds. A step drafted to still post `needs-owner-recheck` for its own exit-2 result would have been describing a state (secret withheld because the PR is a fork or from Dependabot) that is false for this job specifically; that step is not included in the design below.

## Decision

- `scripts/check-paste.mjs` exits 1 when at least one finding is a real content match and 2 when every finding is a config error (`env-unset`, `invalid-json`, `invalid-regexp`, `probe-mismatch`) with no real match; a body that trips both at once exits 1, the real-match case winning.
- `public-surface.yml`'s `check-paste` job computes `TOKEN_RESTRICTED` (a fork head, or `github.event.pull_request.user.login == 'dependabot[bot]'`) and posts `needs-redaction` directly only when the token is not restricted and the exit code is 1. It attempts nothing else — no artifact, no second message — for a restricted run; its `actions/checkout` step still pins `ref` to the PR's base commit, which keeps this job's own execution of `check-paste.mjs` off contributor-controlled code, but this is a narrower guarantee than "trustworthy job" and is not relied on as one.
- A new workflow, `fork-public-surface-notify.yml`, triggers on `workflow_run` for `public-surface.yml`'s completion (`workflow_run` always evaluates the subscriber's own file from the default branch, with a token and secret access that are not fork- or Dependabot-restricted, regardless of what triggered the upstream run). It trusts nothing `check-paste`'s job wrote. Instead it re-derives, from GitHub's API, and then actually performs the check:
  - which open PR the triggering run's commit (`github.event.workflow_run.head_sha`) belongs to, via `GET /repos/{owner}/{repo}/commits/{sha}/pulls` — keyed on a commit SHA GitHub itself attaches to the run, not on anything a workflow step wrote;
  - that PR's current source repository, author, and body, via `gh pr view`;
  - whether this PR actually needed the second stage at all (a fork or Dependabot PR) — recomputed here independently, so a same-repository, non-Dependabot PR (already handled directly) is not double-posted;
  - runs this repository's own default-branch copy of `check-paste.mjs`, with the real `COMPASS_PRIVATE_PATTERNS` secret, against that freshly-fetched body, and posts `needs-redaction` on a real match (exit 1). Exit 2 is not posted: since this job has normal secret access, it can only mean this repository's own secret is itself broken, the same condition `public-surface.yml`'s direct path already treats as a maintainer-side issue to notice from the job log rather than something to put on a PR. There is no `needs-owner-recheck` step in this workflow — the check that step used to ask a maintainer to redo has already run, automatically, by the time this job finishes.
  - a `concurrency` group keyed on the PR's fork repository and branch (stable across the PR's whole open lifetime, unlike its resolved number) queues overlapping runs from rapid successive edits, so the "already labeled" guard on `needs-redaction` sees a prior run's write before deciding whether to post again.
- No workflow in this repository uses `pull_request_target`; `workflow_run` never checks out or executes a fork's code, only a workflow file and scripts already committed to the default branch, evaluated against PR text read through the API — the same shape `check-paste.mjs` was already built to handle safely.

## Consequences

A fork or Dependabot PR's body is now actually checked against `COMPASS_PRIVATE_PATTERNS`, automatically, without a maintainer needing to do anything — a strictly stronger outcome than the notify-and-wait design ADR-0008 first described for this step. The cost is a second workflow run's worth of delay (`fork-public-surface-notify.yml` only starts once `public-surface.yml` finishes) and, for that one check, no visible activity on the PR at all when the body is clean, same as a same-repository PR's own experience. `workflow_run` only fires for a subscriber workflow file already on the default branch, so this path cannot be exercised end-to-end until `fork-public-surface-notify.yml` itself is merged; a fork or Dependabot PR opened before that point still fails the same silent way ADR-0008 originally described for forks.

The `needs-owner-recheck` label no longer has any producer: `check-paste`'s failure mode that used to justify it (secret withheld, check could not run at all) is now always resolved automatically by the second stage rather than reported. The label itself is left defined rather than deleted — deleting it is a separate, out-of-scope repository-administration action, and any PR already carrying it from before this change is unaffected.

Because the second workflow re-derives the PR and its body itself rather than trusting a value the first job passed along, a fork PR author cannot point it at an issue or PR that is not their own commit's associated PR — the commits→pulls lookup is keyed on data GitHub's API attaches to the run, which a workflow file on a contributor's branch cannot rewrite.

`workflow_run` subscribes by the triggering workflow's name, matched against whichever copy of `public-surface.yml` actually ran — for a `pull_request` run, that is the fork PR's own branch. A fork PR author can rename or remove that job in their own branch so `fork-public-surface-notify.yml`'s `workflows: ["Public surface"]` never matches their run, silently suppressing the second stage — and now the check itself, not just a notification about it — for their own PR. This only affects that PR: it does not let anyone act on another PR (the provenance guarantee above is unrelated to this), and `ci.yml`'s `check` job stays red on every fork PR regardless, so the merge gate itself is untouched. This is recorded here as a known, accepted trade-off rather than a solved problem, consistent with ADR-0008's own framing of the risk `fork-recheck.yml` leaves to manual review.

This amends ADR-0008's "Flag needs-owner-recheck" bullet: that step no longer exists. What ADR-0008 called "the maintainer clears that failure" for this specific check is now automatic; ADR-0008's decision against `pull_request_target`, and everything it says about `ci.yml`'s own `check` job and `fork-recheck.yml`, stands unchanged.
